Part II – Technical Reference

This part summarises the technical data of the EBCTester board and the firmware: start-up behaviour, connectors, firmware defaults, data storage, interfaces and security. A complete reference for developers and makers is contained in the Maker Edition of this manual.

This part is intended for readers who build the hardware themselves, compile the firmware, integrate EBCTester into other systems or want to understand how it works internally. It covers the start-up and configuration logic, the reference circuit, connectors and parts, firmware configuration, the tester protocol, data storage, interfaces and security.

System architecture

The firmware is written in C/C++ with Espressif's ESP-IDF 6.0.1 for the ESP32-S3. Tester communication, test control, recording, the charts and the optional services are separate components; networking, firmware updates and SD-card handling are reusable libraries (OTA Suite, SD Card Manager).

Firmware structure

The firmware is written in C/C++ with Espressif's ESP-IDF 6.0.1 for the ESP32-S3. It is divided into functional components; the main program only initialises services. Networking, updates and SD-card handling are separate, reusable repositories included as Git submodules under external/.

Data flow

The tester sends a status message roughly once per second. ebc_link checks each message (checksum, model identifier) and passes it to the controller. While a test is active, test_store averages a configurable number of messages (default 20, about one stored measurement every 20 seconds) and writes the measurement in a database transaction to the SD card. Plans and DCIR tests are state machines running in their own tasks; they react to the received messages and send commands to the tester. The web interface only reads data and sends commands through authenticated HTTP requests – it is never needed for a test to continue.

GPIO 47 detection

The level of GPIO 47 is determined without loading the pin permanently:

  1. The internal pull-up is switched on; after 200 µs the pin is read.
  2. The internal pull-down is switched on; after 200 µs the pin is read again.
  3. Steps 1–2 are repeated three times. Afterwards both pull resistors are switched off and the pin is disabled, so no current flows through the internal resistor during operation.
Read with pull-upRead with pull-downResultMode
10open (pin follows the internal resistor)MakerMode
00low (tied to GND)MakerMode
11high (tied to 3.3 V)FactoryMode
01inconsistent (interference)MakerMode, warning in the log

The pull-up is "1" only if it is 1 in all three passes; the pull-down result is "1" if it is 1 in any pass. An external connection must be clearly stronger than the internal resistors (about 45 kΩ): use a direct connection or a resistor of at most 10 kΩ. On the original board, solder jumper JP1 ties GPIO 47 directly to 3.3 V (pads 1–2, as delivered) or to GND (pads 2–3).

Configuration storage

All hardware-related settings are stored in the NVS namespace ebc_cfg. After the first start the firmware uses only these stored values; the build configuration (sdkconfig) only supplies the defaults for a new configuration.

KeyTypeContent
configblobHeader (magic 0x45424332 "EBC2", structure version 1, payload length, CRC-32) followed by the complete configuration structure
FirmwareModeu80 = MakerMode, 1 = FactoryMode
ConfigAktiveu80 = inactive (setup only), 1 = active

The configuration is written in the order blob – FirmwareMode – ConfigAktive and then committed. The blob is written as a whole: after a power failure during writing either the old or the new version is present.

Validity check

A stored configuration is valid only if the namespace exists, the blob has the expected size, magic and structure version, the CRC-32 over the payload is correct, FirmwareMode exists and the content passes the general checks of Activation and validation. The start-up log reports the result: new, new or invalid size/magic, version mismatch, CRC mismatch or valid. A missing or invalid ConfigAktive starts the device inactive; an active configuration that fails the pin checks also starts inactive.

If nvs_flash_init() reports a full or incompatible NVS partition (for example after an interrupted erase), the partition is erased and initialised again; the device then starts like a new one.

Circuit description

Power supply

The 19 V input (from the EBC-A20 power supply via J4) is protected by the unidirectional TVS diode D3 (SMBJ20A, cathode to +19 V; stand-off voltage 20 V, clamping voltage 32.4 V – below the 35 V absolute maximum input of U2). D3 also protects against reverse polarity by conducting, so the supply should be current-limited or fused. The synchronous buck converter U2 (AP63205, fixed 5 V, up to 2 A) with L1 (4.7 µH) produces 5 V. This output and the USB supply (VBUS) are combined by the Schottky diodes D1 and D2 (SS34) into the +5 V rail, which is about 4.6–4.7 V after the diode drop. The board can therefore run from the 19 V input, from USB, or from both at the same time. With USB only, the total current is limited to the 500 mA of the USB port.

A second buck converter U3 (AP63203, fixed 3.3 V) with L2 supplies the ESP32-S3 and all logic from the +5 V rail, so 3.3 V is available from either source. Input and output capacitors follow the Diodes Inc. data sheet: 10 µF/50 V at the 19 V side, 2 × 22 µF at each output, 100 nF bootstrap capacitors. The data sheet suggests 3.9 µH for the 3.3 V version; 4.7 µH is within the permitted range (2.2–10 µH).

Microcontroller and USB

U4 is an ESP32-S3-WROOM-1U-N16R8 module with 16 MB flash and 8 MB octal PSRAM. The "U" variant has no PCB antenna but a u.FL connector – an external 2.4 GHz antenna is mandatory. GPIO 35–37 are used internally by the octal PSRAM and must not be used. The USB-C connector J2 is wired to the native USB of the ESP32-S3 (GPIO 19/20) for flashing and the console; D4 (USBLC6-2SC6) protects the data lines against ESD. R10/R11 (5.1 kΩ on CC1/CC2) identify the board as a USB device to USB-C power supplies.

SW1 (BOOT, GPIO 0, pull-up R12) and SW2 (RESET, EN, pull-up R13 with C16 for a defined power-on reset) allow manual download mode: hold BOOT, press and release RESET, release BOOT.

microSD card

J1 (Hirose DM3AT) is connected in 4-bit SD mode. All data and command lines have 10 kΩ pull-ups (R1–R5) as required by the SD specification. The card-detect switch is normally open and closes when a card is inserted; with pull-up R6, the signal SD_CD reads low with a card present.

Real-time clock

U1 (DS3231SN) is a temperature-compensated RTC (±2 ppm) on I²C with 4.7 kΩ pull-ups (R7/R8). Its INT/SQW output (open drain, pull-up R9) goes to GPIO 14 and can be used as an interrupt or deep-sleep wake-up source. A non-rechargeable CR2032 cell (BT1) on VBAT keeps the time when the board is unpowered; the cell voltage can be measured at TP11. Firmware 1.99.3 does not use the RTC yet; the time is obtained by SNTP when Wi-Fi with Internet access is available.

Serial interface

The tester uses 5 V TTL levels, but ESP32-S3 inputs are not 5 V tolerant. U5 (TXS0104E) is a 4-bit bidirectional, auto-direction level shifter between 3.3 V (VCCA) and the +5 V rail (VCCB). It carries UART1 (tester) and UART2 (reserved for the PC dongle) to connector J4. The TXS0104E is suited to push-pull signals at the low baud rate used (9600 Bd).

Status LEDs

LED1 and LED2 are WS2812B RGB LEDs with integrated driver, connected in a chain to GPIO 48 through the series resistor R15 (470 Ω). Each LED has a 100 nF decoupling capacitor (C17, C18). The WS2812B runs on the +5 V rail, but the ESP32 drives the data line with 3.3 V. To keep this level above the input-high threshold of LED1 (0.7 × VDD), LED1 is supplied through the Schottky diode D5, which lowers its supply by about 0.3 V. LED2 receives the regenerated 5 V signal from LED1. The data output of LED2 is led through R16 (470 Ω) to connector J5, so that further WS2812B LEDs can be added to the chain. Firmware 1.99.3 drives LED1 only.

Power-OK LED and mode jumper

D6 is connected to +3.3 V through R14 (470 Ω) and lights up as soon as the 3.3 V supply is present – independently of the firmware. The three-pad solder jumper JP1 ties GPIO 47 to +3.3 V (pads 1–2, bridged as delivered) or to GND (pads 2–3) and selects the firmware mode at the first start.

Firmware installation and build

Installing a release

Each GitHub release contains EBCTester-<version>-full-install.bin with bootloader, partition table and application. Flash it at address 0x0 with esptool (see belowInstalling the firmware). Updates are normally installed over Wi-Fi; a USB installation is only needed for the first installation, after a change of the partition table or for recovery.

esptool.py --chip esp32s3 --port COM5 write_flash 0x0 EBCTester-1.99.3-full-install.bin

Writing the full image does not erase the settings memory. To start like a new device afterwards, use the device reset or the USB erase described in Troubleshooting.

Building from source

Requirements: VS Code with the ESP-IDF extension, ESP-IDF 6.0.1, Git and an Internet connection for the first build (managed components and the SQLite source are downloaded and hash-checked).

git clone --recurse-submodules https://github.com/Gemelon/EBCTester.git
# existing checkout:
git submodule update --init --recursive
  1. Open the project in VS Code and select the ESP-IDF environment and target esp32s3.
  2. Review the defaults in menuconfig (see below).
  3. Build with ESP-IDF: Build your project.
  4. For the first installation, flash bootloader, partition table and application over USB.

A ZIP download of the repository does not contain the submodules. Do not run git submodule update --remote without reviewing the changes – the main repository records the tested versions. sdkconfig.defaults provides portable defaults; an existing local sdkconfig takes priority. Size optimisation (-Os) is the default.

Communication with the tester

Serial interface

UART1 is connected to the tester with 9600 baud, 8 data bits, odd parity, 1 stop bit (8O1) at 5 V TTL level. Frames start with 0xFA and end with 0xF8. Status frames are 19 bytes long. An XOR checksum over bytes 1–16 is verified before any data is used. The EBC-A20 transmits checksums in the range 0xF0–0xFF with the upper nibble cleared, to avoid the frame markers; this variant is also accepted.

Set-points are transmitted as two bytes in base 240 (value = high × 240 + low) with a resolution of 0.01 A or 0.01 V. The range is sufficient for 50 A; the 10 mA resolution has not been verified on real A50L hardware yet. The discharge command also carries a time limit in whole minutes.

Model detection

Byte 16 of each status frame contains the model identifier (normalised as raw value modulo 100). For status bytes of at least 100, bytes 10 and 11 contain the tester's firmware version (B10 × 240 + B11), which distinguishes variants with the same identifier.

Tester interface

UART1 is connected to the tester with 9600 baud, 8 data bits, odd parity and 1 stop bit (8O1) at 5 V TTL level. Every status frame is checked (frame markers, XOR checksum, model identifier) before its data is used.

Data storage

SQLite database on the SD card

The database file is /sdcard/ebc_a20.db. It is created when a card is mounted; if the device starts without a card, it is created as soon as one is inserted. The card is never formatted and an existing database is never deleted. A file without a valid SQLite header is preserved under the name ebc_a20.db.invalid-XXXXXXXX before a new database is created.

MariaDB backup database

The MariaDB synchroniser copies plans, steps, batteries, runs, segments, measurements and DCIR results to an existing MariaDB schema (for example ebc_a20). Progress is tracked per run; only new data is sent in batches of 200 rows with INSERT IGNORE.

  • The base schema (migrations 001–005) must exist on the server. The repository contains migration sql/006_resistance_results_mariadb.sql for DCIR results, not a complete initial schema.
  • The user needs a mysql_native_password account with SELECT/INSERT/UPDATE on ebc_test_plan, ebc_battery, ebc_test_run, additionally DELETE on ebc_test_plan_step, and INSERT on ebc_run_segment and ebc_measurement, plus rights on the DCIR result table.

  • The connection is plain TCP without TLS.

Home Assistant MQTT topics

On connection the device publishes a retained discovery document to homeassistant/device/ebctester_<MAC>/config, its availability (online / offline as Last Will) to <prefix>/availability, and every recorded measurement (voltage, current, capacity) as a non-retained QoS 0 message to <prefix>/state. Mode, plan status and battery entities are already announced but do not yet receive values. Commands are accepted on <prefix>/command as a JSON object:

{"command":"start_plan"}        (only if remote start is allowed)
{"command":"stop"}
{"command":"abort"}
{"command":"select_plan","name":"Plan name"}
{"command":"select_battery","name":"Battery label"}

MQTT cannot set free set-points or create database entries. Invalid commands are ignored. Failed connections are retried with increasing intervals from 1 to 60 seconds.

Firmware updates and publishing

Update procedure

  • The device downloads only the manifest firmware.json (after Wi-Fi connects, every six hours, when the UI is opened). HTTPS checks wait for a synchronised clock. Inactive Maker devices do not check.
  • Versions must be strictly numeric major.minor.patch and newer than the installed one.
  • Manifest and image must be delivered directly (HTTP 200, no redirects). HTTPS validates certificate chain, host name and dates. HTTP is only possible with the explicit option for a trusted test network.
  • The image is streamed into the inactive slot; exact size and SHA-256 are checked before it is selected for booting. Project name and target must match.
  • After restart the new firmware must run for 10 seconds; an earlier reset or crash rolls back to the previous version.

Manifest format

{
  "project": "EBCTester",
  "target": "esp32s3",
  "version": "1.99.4",
  "url": "https://updates.example.org/BatteryTester/EBCTester-1.99.4.bin",
  "size": 2825440,
  "sha256": "<64 lower-case hex digits>",
  "notes": "Release notes"
}

All seven fields are mandatory; the manifest must be smaller than 2048 bytes, notes at most 512 bytes. The image URL must be in the same directory as the manifest and named <project>-<version>.bin.

Publishing your own builds

Publishing is disabled in a fresh checkout. It is enabled with a local, Git-ignored file CMakeUserConfig.cmake (see README). A successful build then creates the immutable versioned image, a compatibility copy and finally the manifest, optionally uploaded by SFTP. A published version is never overwritten with different content – increase the version first. Always distribute the license directory together with the firmware.

Security and limitations

Security

  • Login: user admin with the login password (initially ebctester). The password, the session duration and the login switch are stored in the device configuration (ebc_cfg). Sessions use a random 256-bit cookie (HttpOnly, SameSite=Lax), last exactly 1 or 7 days and are held in RAM (a restart ends them). At most 8 sessions at a time; failed logins are delayed by one second.
  • Settings protection: all changing requests require a CSRF token; settings additionally require the current login password, independent of whether browser login is enabled. Password or login-policy changes invalidate all sessions.
  • Access point: the access-point password is defined by the firmware and cannot be changed in the browser on a Factory device. Keep the access point in a trusted environment and connect the device to your own Wi-Fi.set a personal access-point password in Maker Settings; the firmware default is the same on every device.
  • Transport: the web interface, MQTT and MariaDB are unencrypted. Use only trusted networks, never forward port 80 to the Internet.
  • Storage: NVS and flash are not encrypted by default; protect physical access and the USB port (the start-up log shows a generated access-point password). Change the shared initial login password ebctester on first use.
  • Firmware: SHA-256 protects against corruption, not against deliberate replacement. Secure Boot, signed images and flash encryption are separate deployment decisions.

Known limitations (firmware 1.99.3)

  • Firmware 1.99.3 is a beta version of V2. The hardware acceptance tests on the original board are still pending.
  • The UART2 bridge for the manufacturer's PC software is not implemented.
  • The DS3231 real-time clock is not used yet; date and time come from SNTP only.
  • Only EBC-A20, EBC-A40L and EBC-A50L can be controlled; physical tests with the A50L are pending.
  • No battery-chemistry profiles and no temperature measurement.
  • MQTT publishes measurements only; status entities do not yet receive values.
  • LED2 of the original board is not driven yet.
  • The card-detect input is active-high only.
    •
  • A forgotten login password can only be reset by erasing the settings memory over USB.
